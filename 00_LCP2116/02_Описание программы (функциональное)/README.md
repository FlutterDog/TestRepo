# LCP Basic Diagnostic Firmware

Базовая диагностическая прошивка контроллера LCP предназначена для проверки аппаратной платформы на микроконтроллере ATSAM3X8E и используется как исходная промышленная база для дальнейшей разработки прикладного программного обеспечения контроллера.

Прошивка проверяет основные аппаратные узлы платы, формирует единый HAL/platform-слой проекта и предоставляет USB service console для диагностики.

## Как пользоваться Doxygen-документацией

Doxygen-документация — это HTML-справочник по исходному коду прошивки. Она не заменяет исходники и не является отдельной инструкцией по эксплуатации контроллера. Её назначение — быстро показать структуру проекта, назначение файлов, публичные интерфейсы модулей и связи между уровнями прошивки.

Документация формируется автоматически из:

- `README.md`;
- Doxygen-комментариев в `.hpp`, `.h`, `.cpp`, `.c`;
- структуры файлов и классов проекта.

### Что смотреть в первую очередь

Начинать нужно с вкладки **«Титульная страница»**. Это главная страница проекта. В ней описаны назначение baseline-прошивки, состав проекта, аппаратные узлы, диагностические команды, порядок сборки, загрузки и проверки.

Далее удобно переходить в раздел **«Файлы»**. Этот раздел показывает структуру исходного кода по каталогам. Для сопровождения прошивки это основной рабочий раздел. Через него удобно открывать:

- `app/app.cpp` — общий порядок инициализации и основной цикл;
- `app/diagnostics/diagnostic_console.cpp` — команды USB service console;
- `board/` — аппаратная карта платы;
- `hal/` — низкоуровневые драйверы ATSAM3X8E и внешних микросхем;
- `platform/` — собственный платформенный API проекта;

Раздел **«Классы»** показывает только структуры и классы C++: например `SerialPort`, `SPIClass`, `W5500NetworkConfig`, `Sam3xRtcDateTime`. Он не является полным реестром всех функций прошивки. Для embedded C/C++ проекта значительная часть логики находится в свободных функциях и модулях `.cpp/.hpp`, поэтому основной обзор нужно вести через **«Файлы»**, а не только через **«Классы»**.

### Как читать раздел «Файлы»

В разделе **«Файлы»** каждый файл открывается как отдельная страница. На странице файла обычно есть:

- краткое описание назначения файла;
- список классов, структур, enum и функций;
- ссылки на объявления;
- ссылки на реализацию функций;
- исходный код, если включён просмотр source listing.

Для быстрого понимания модуля сначала читать заголовочный файл `.hpp`, потому что в нём описан публичный контракт модуля. Файл `.cpp` читать после этого, когда нужно понять реализацию.

### Как читать раздел «Классы»

Раздел **«Классы»** полезен для просмотра структур данных и интерфейсных классов.

Примеры:

- `SerialPort` — платформенный интерфейс аппаратного последовательного порта;
- `SPIClass` — платформенный SPI master;
- `Sam3xRtcDateTime` — структура даты и времени RTC;
- `Sam3xWatchdogConfig` — структура конфигурации watchdog;
- `W5500NetworkConfig` — конфигурация Ethernet-интерфейса W5500.

Если нужной функции нет в разделе «Классы», это нормально. Свободные функции находятся в разделе **«Файлы»** на страницах соответствующих модулей.

## Назначение baseline-прошивки

Прошивка предназначена для базовой проверки контроллера LCP после сборки, ремонта, изменения схемы или переноса проекта.

Проверяются:

- запуск микроконтроллера ATSAM3X8E;
- heartbeat-индикация `PLC_ok`;
- USB CDC service console;
- переход в ROM SAM-BA/BOSSA загрузчик через 1200 bit/s;
- встроенные RS-485 порты;
- внешние UART на SC16IS7xx;
- Ethernet-контроллеры W5500;
- microSD-карта и FAT16/FAT32;
- цифровой контроль батареи CR2032;
- локальный RTC;
- сохранение RTC при отключении основного питания;
- watchdog-reset;
- восстановление USB CDC после watchdog-reset.

Прошивка не содержит прикладную логику ПЛК, Modbus TCP server, IEC 60870-5-104 server, SNTP и рабочую конфигурацию объекта. Эти функции добавляются поверх baseline-версии отдельными этапами.

## Архитектура

### `main.cpp`

Точка входа программы.

Выполняет:

- системную инициализацию;
- запуск системного тика;
- вызов `setup()`;
- бесконечный вызов `loop()`.

### `app/`

Прикладной уровень baseline-прошивки.

Содержит:

- последовательность инициализации диагностических модулей;
- основной цикл обслуживания диагностик;
- USB service console;
- команды диагностики;
- heartbeat-индикацию;
- диагностику периферии;
- обслуживание watchdog.

### `app/diagnostics/`

Диагностические модули.

Каждый модуль отвечает за одну аппаратную область:

| Модуль | Назначение |
|---|---|
| `diagnostic_console.*` | USB service console и обработка команд |
| `rs485_echo_test.*` | echo-test встроенных RS-485 портов |
| `sc16is_echo_test.*` | echo-test внешних UART SC16IS7xx |
| `ethernet_echo_test.*` | TCP echo-test W5500 |
| `sd_card_test.*` | проверка microSD и FAT |
| `battery_status.*` | контроль CR2032 через цифровой вход компаратора |
| `rtc_status.*` | чтение и установка локального RTC |
| `watchdog_status.*` | watchdog и восстановление после watchdog-reset |

### `board/`

Board-слой LCP.

Содержит привязку аппаратных сигналов платы к платформенным выводам и инициализацию узлов платы.

Прикладной код не должен напрямую дублировать карту выводов. Изменения аппаратной карты выполняются в `board/`.

### `hal/`

Аппаратно-зависимый слой ATSAM3X8E.

Содержит:

- GPIO;
- SPI;
- UART/USART;
- системный тик;
- RTC;
- watchdog;
- драйвер SC16IS7xx;
- минимальный драйвер W5500.

### `platform/`

Платформенный совместимый слой проекта.

Содержит удобные прикладные интерфейсы:

- `pinMode()`;
- `digitalWrite()`;
- `digitalRead()`;
- `millis()`;
- `micros()`;
- `delay()`;
- `Serial`;
- `Serial1`;
- `Serial2`;
- `Serial3`;
- `SPI`;
- `Print`.

Этот слой является собственным платформенным API проекта и не должен рассматриваться как внешняя среда разработки.

### `libs/lcp_sd_storage/`

Минимальный слой работы с microSD и FAT16/FAT32.

Поддерживает:

- инициализацию SD-карты через SPI;
- чтение блоков;
- запись блоков;
- монтирование FAT16/FAT32;
- поиск файла в корневом каталоге;
- чтение файла;
- запись файла с заменой существующего.

Ограничения baseline-версии:

- только корневой каталог;
- только имена 8.3;
- без длинных имён;
- без подкаталогов;
- без одновременного открытия нескольких файлов.

### `libs/SAM_USB/`

Низкоуровневый USB CDC service layer.

Он используется для:

- USB CDC service console;
- USB descriptors;
- endpoint handling;
- 1200 bit/s boot trigger.

Этот слой не включается в Doxygen как собственный прикладной код проекта.

## Аппаратная карта baseline-диагностики

### USB

| Назначение | Описание |
|---|---|
| USB CDC service console | Основной диагностический интерфейс |
| 1200 bit/s trigger | Переход в ROM SAM-BA/BOSSA bootloader |
| VID/PID | сервисная engineering identity текущей прошивки |

Идентификаторы USB заданы в `board/lcp_usb_identity.hpp`.

Значения engineering VID/PID используются для baseline-версии. Для серийного продукта владелец проекта должен заменить их на собственные идентификаторы.

### Встроенные RS-485

| Линия | Объект | Назначение |
|---|---|---|
| X2X | `Serial` | echo-test, 9600 bit/s, 8N1 |
| S2 | `Serial1` | echo-test, 9600 bit/s, 8N1 |
| S4 | `Serial2` | echo-test, 9600 bit/s, 8N1 |
| S3 | `Serial3` | echo-test, 9600 bit/s, 8N1 |

Управление направлением RS-485 выполняется HAL UART/USART.

### SC16IS7xx

Поддерживается проверенная аппаратная конфигурация:

```text
UART1_CS CH_A: PC
UART2_CS CH_A: HMI
UART3_CS CH_A: S1
```

`UART2_CS CH_B` отсутствует в проверенной ревизии.

### Ethernet W5500

| Интерфейс | CS | IP | TCP echo port |
|---|---:|---|---:|
| ETH1 | 10 | 192.168.1.1 | 5001 |
| ETH2 | 48 | 192.168.1.1 | 5002 |

Используется socket 0 каждого W5500.

### microSD

| Сигнал | Значение |
|---|---|
| CS | 23 |
| Detect | 25 |
| SD_OK | 41 |
| Detect logic | active high |

Команда `sd test` создаёт и читает файл `SDTEST.TXT`.

### CR2032

| Параметр | Значение |
|---|---|
| Контрольный вход | PIN50 |
| Порог компаратора | 2.2 V |
| Нормальное состояние | `Vbat > 2.2 V` |
| Аварийное состояние | `Vbat < 2.2 V` |

При снижении напряжения выводится сообщение:

```text
replace CR2032 battery
```

### RTC

Локальный RTC ATSAM3X8E работает от внешнего 32.768 kHz кварца.

Поддерживаются команды:

```text
rtc
rtc set 2026-06-08 21:06:30
rtc set 26-06-08 21:06:30
```

Год `0..99` трактуется как `2000..2099`.

### Watchdog

Watchdog включён в проверенном режиме:

```text
WDRPROC = 1
WDRSTEN = 1
WDV = 1024
WDD = 4095
```

Период watchdog составляет 4000 ms. Основной цикл перезапускает watchdog каждые 500 ms.

После watchdog-reset прошивка выполняет один software reset через `RSTC_CR` с `PROCRST | PERRST`. Это восстанавливает USB CDC после watchdog-события.

## USB service console

После подключения к USB CDC в терминале выводится:

```text
LCP diagnostic firmware ready. Type help.
```

Параметры терминала:

```text
115200 bit/s
8N1
no flow control
```

Скорость для USB CDC не влияет на физическую скорость USB, но используется как стандартный параметр терминальной программы.

## Проверка baseline-прошивки

### Проверка версии

```text
version
```

Ожидаемый вывод:

```text
LCP Basic Diagnostic Firmware
version=0.16.3
stage=Stage 16D
target=ATSAM3X8E
```

### Проверка полного статуса

```text
status
```

Ожидаемые признаки:

```text
USB service CDC: open
error_count=0
SC16IS probe done
W5500 status
filesystem ready=yes
state=ok
RTC_VER=0x0
watchdog_usb_recovery=performed или not performed
enabled=yes
```

### Проверка microSD

```text
sd
sd test
```

Ожидаемые признаки:

```text
card inserted=yes
filesystem ready=yes
save SDTEST.TXT: ok
load SDTEST.TXT: ok
microSD file test OK
```

### Проверка RTC

```text
rtc set 2026-06-08 21:06:30
rtc
```

Ожидаемые признаки:

```text
rtc set result=ok
datetime=2026-06-08 21:06:30
RTC_VER=0x0
registers valid=yes
```

После отключения и повторного включения основного питания RTC должен продолжить ход времени от CR2032.

### Проверка watchdog

```text
watchdog
watchdog test reset
```

После `watchdog test reset` USB CDC должен отключиться и появиться снова. Терминальную сессию нужно открыть заново.

Ожидаемые признаки после повторного подключения:

```text
watchdog_usb_recovery=performed
last_reset=software reset
enabled=yes
WDT_MR=0xFFF6400
```

## Загрузка прошивки

Для загрузки используется BOSSA/bossac через ROM SAM-BA/BOSSA bootloader ATSAM3X8E.

Общий порядок:

1. Перевести контроллер в ROM bootloader.
2. Дождаться появления BOSSA/SAM-BA COM-порта.
3. Запустить `bossac`.
4. Дождаться окончания записи.
5. Перезапустить контроллер.
6. Открыть USB service console application firmware.
7. Выполнить `version` и `status`.

Пример команды:

```bat
bossac.exe -i -d --port=COM10 -U true -e -w -v -b LCP_Basic.bin -R
```

Порт `COM10` заменить на фактический BOSSA/SAM-BA порт.

## Переход в bootloader через 1200 bit/s

Application firmware поддерживает переход в ROM SAM-BA/BOSSA bootloader через открытие USB CDC порта на скорости 1200 bit/s с последующим закрытием порта.

После срабатывания trigger application COM-порт пропадает, и появляется ROM SAM-BA/BOSSA COM-порт.

## Генерация Doxygen-документации

Doxygen-документация формируется из `README.md` и исходных файлов проекта.

Вход Doxygen:

```text
README.md
main.cpp
app/
board/
hal/
platform/
libs/lcp_sd_storage/
```

Исключено из Doxygen:

```text
libs/SAM_USB/
Device_Startup/
docs/doxygen/
Debug/
Release/
.vs/
```

### Быстрый запуск

Из корня проекта:

```bat
if not exist docs mkdir docs
if not exist docs\doxygen mkdir docs\doxygen
doxygen Doxyfile
```

### Запуск с логом

```bat
if not exist docs mkdir docs
if not exist docs\doxygen mkdir docs\doxygen
doxygen Doxyfile > docs\doxygen\doxygen_build.log 2>&1
```

HTML-документация:

```text
docs\doxygen\html\index.html
```

Открытие результата:

```bat
start docs\doxygen\html\index.html
```

## Ограничения baseline-версии

- Прошивка является диагностической baseline-базой, а не полной прикладной ПЛК-прошивкой.
- Modbus TCP server не реализован в baseline.
- IEC 60870-5-104 server не реализован в baseline.
- SNTP не реализован в baseline.
- Прикладная конфигурация объекта не реализована в baseline.
- microSD-слой поддерживает только root-каталог и имена 8.3.
- USB service layer оставлен как низкоуровневый служебный слой и не включён в Doxygen как собственный прикладной код.

## Рекомендации по сопровождению

Перед изменениями:

1. Собрать проект без изменений.
2. Сохранить рабочий `.bin`.
3. Выполнить `version`.
4. Выполнить `status`.
5. Проверить USB service console.
6. Проверить watchdog recovery.
7. После изменений повторить полный baseline-тест.

Изменения аппаратной карты выполнять в `board/`.

Изменения низкоуровневых драйверов выполнять в `hal/`.

Изменения диагностических команд выполнять в `app/diagnostics/diagnostic_console.cpp`.

Изменения версии выполнять в `app/version.hpp`.
